# Runbook: TIA Bill Second Reading — Friday 11 September 2026

Verified from the store, not from memory: **Friday 11 September**,
9.30am Commons Private Members' Bills, "Terminally Ill Adults (End of
Life) Bill: Second Reading" (What's On item); board 4157 sits at
`2nd reading` with `next_key_date 2026-09-11`, status live; the issue
`assisted-suicide-2026` is still marked `upcoming: true`.

The day's risk is not fetching data. It is attaching a MEANING to a
question nobody read — the Lords inversion (2026-08-31) and the EU
ePrivacy fast-track (2026-09-01) were both that mistake caught late.
So the tool refuses to draft anything it cannot anchor-test.

## The whole day, in one command

    python3 tools/prep_division.py --date 2026-09-11

Prints every Commons division of the day with ids and tallies, then the
Hansard and Votes-and-Proceedings links, and stops. It stops because of
a measured fact: **the Commons API carries no question text.** Checked
across 40 archived division payloads — `FriendlyDescription` and
`FriendlyTitle` are null in every one, and there is no motion-notes
field at all (the Lords API has one; that asymmetry is why the Lords
inversion was catchable there and why nothing here may be assumed).

Read the question from Hansard. Then:

    python3 tools/prep_division.py --date 2026-09-11 --our-side no

which fetches the name lists, runs the anchor test, and — only if it
passes — prints the config block and the sign-off message ready to send.

## The anchor test (what makes this safe)

Three members with measured, consistent records on assisted suicide
across both the 2024 and 2025 readings, from the archived name lists:

| Member | Record | Must render |
|---|---|---|
| Danny Kruger | No, both readings | **GOOD VOTE** |
| Kim Leadbeater | Aye, both readings | **BAD VOTE** |
| Lauren Edwards (sponsors the 2026 Bill) | Aye, both readings | **BAD VOTE** |

Each expectation is fixed to the PERSON, deliberately not derived from
the proposed `our_side`. The first version of this tool did derive it,
which made the test a tautology that passed a fully inverted verdict
without complaint; fed `--our-side aye` on the known Third Reading it
printed "Anchors check out". Now the same input is refused, and a
regression test pins it. Fewer than two voting anchors = untestable, and
it fails closed rather than passing on silence.

Rehearsed against a known answer before the day:

    python3 tools/prep_division.py --rehearse

reproduces 20 June 2025 — division 2071, 314–291, Kruger GOOD,
Leadbeater BAD, Edwards BAD — matching the verdict signed weeks ago.

## Judgement the tool cannot make

- **A reasoned amendment inverts the polarity.** Its question is to
  decline a second reading, so Aye = against the Bill, and the Second
  Reading meanings must NOT be reused. Its own entry, its own
  `our_side`, its own sign-off.
- **A closure motion is a separate division** and a separate call
  (the ePrivacy precedent: the EU roll call everyone would have read as
  "the scanning derogation" was in fact the fast-track motion).
  Whether it gets a verdict at all is Christopher's.
- **Several divisions, several verdicts.** The rehearsal found six
  divisions on 20 June 2025; the tool refuses a whole-day verdict and
  asks for `--division <id>` when a stage title is ambiguous.

## Before the sign-off: the brief

The Division watch (`.github/workflows/division-watch.yml`) runs at 13:00,
15:00 and 17:00 UTC on Fridays. For every division of the day on our
ground it writes `data/briefs/division-c<id>.md` -- result, party
splits, the three anchors' lobbies, who changed lobby since the 2025
Third Reading, full name lists by lobby -- and DMs one message with the
links. To run it by hand:

    gh workflow run division-watch.yml -f date=2026-09-11

It attaches no meaning. The brief is the raw material of the emails; the
verdict is still the two commands above.

`Deploy tracker` pulls the store, runs the suite as a gate, rebuilds the
tracker and deploys the partner site. It never writes the store. Locally
the same rebuild is:

    python3 tools/make_vote_tracker.py
    git add -A && git commit && git pull --rebase && git push
    gh workflow run monday-publish.yml -f dry_run=true   # watch, grep for traceback
    git push origin origin/main:live

Verify on the built page, never by reasoning: Leadbeater's band hero
shows her new vote line; the record card carries the division inside
"The full journey"; one 2025 No-voter checked for a flip.

## If there is no division

- **Talked out, or closure fails** — nothing is signed. Update the
  issue `status:` line and the board's next key date when the new date
  is announced; the band keeps the Bill either way.
- **Passed on the nod** — no member votes exist to judge. Status line
  only; the band's "vote will appear here" promise becomes what
  actually happened.
- **Votes API lagging** — the tool says so and tells you to retry.
  Never build from press reports.

## Not this runbook's job

The Slack top-five and the Breakfast Briefing carry the news on their
own tracks. Briefs are untouched (the Bill already has its evergreen
petition action). Lords stages, if it passes, get their own entries when
they divide — with the same discipline applied to each motion.
