Five columns is the most a Slack canvas carries comfortably on a phone; the Consultations section already uses a two-column table, so tables are proven in both destinations. The table wins on scanning a busy week; the diary wins on reading a quiet one.

What has to change in the renderer for either B or C

  1. Carry the event, not just the verdict. Today each Week-ahead line is the judge's why-line alone. The What's On event already holds StartTime/EndTime, House, Type, Description and the leading Member; the line must lead with them and carry the why-line beneath.
  2. One line per event. Events are stored once per horizon (week / further) with different ids, so each is judged twice and printed twice. Key the item on Parliament's own event Id (56333), and the duplicate — and the duplicated spend — disappears.
  3. Link to the substantive source, then the diary. "e-petition 763161" → petition.parliament.uk/petitions/763161; a Bill → bills.parliament.uk via the bills board (What's On leaves BillId empty); every event → whatson.parliament.uk/event/cal<Id>. A Hansard link can be added after the fact by the Sunday pull.
  4. Dates as a reader writes them. "Monday 7 September", not "Monday 2026-09-07"; times as "4.30–6.00pm", not "16:30".
  5. Start the week on Monday. Friday 4 September is last week and belongs in Parliamentarians on our issues, with the votes. The section should begin at week_commencing.
  6. Show the score once. The 3/2/1 badge in front of the why-line tells the reader which lines were campaign triggers without re-reading the prose.

Held constant: why-lines are the judge's and are not edited; action labels never carry a deadline; nothing is invented — every link is built from a field Parliament publishes.
